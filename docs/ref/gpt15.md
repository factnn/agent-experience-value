真正不同架构，例如 MoE，要不要？
目前不作为必需项。

Qwen 与 Llama 的这类模型仍属于 Transformer 路线；换家族主要改变模型训练背景及具体设计，不是严格控制其他条件后的“架构因果实验”。

要检查 dense 与 MoE 的差异，可以考虑额外的 MoE 对照，但这是另一条轴。例如 Qwen3-30B-A3B 官方报告的是 30.5B 总参数、3.3B 激活参数，不能把它按普通 3B 模型估算权重内存和训练成本。

**所以第一篇先争取“两个规模、两个家族”，不必同时要求“dense、MoE、其他混合架构全部覆盖”。**只有结论需要跨架构解释时，再补对应实验。

五、跨模型最需要保持的，是比较含义，而不是机械照抄所有数字
这部分要提前告诉执行端，避免再花钱测到接口差异。

**每个模型内部，各经验分支必须使用同一个起点、同一训练配方和预算规则。**跨模型则各有自己的起点与采样前信号，不能把 4B 的历史、模板或 adapter 直接当成新模型的实验条件。

**模型应该使用正确的原生接口。**例如 Qwen 的 thinking 模式与 Llama 的工具消息模板并不是同一个开关；不能为了表面上“统一 prompt”，让一个模型正常调用、另一个模型一直格式失败。两者官方用法有明确区别。

**跨模型的同 token 预算，不应直接解释成同计算成本。**我们可以保持一致的预算定义来比较经验价值关系，同时报告实际采样、输入处理量和 GPU 开销；不要把模型间所有变化因果归到参数规模。

还有实际资源问题：仓库此前盘点的是 A100-SXM4-40GB，且当时检查的目录没有完整可用的 8B 或另一家族权重。不能依据 4B 能跑，就认定 8B 在当前最长轨迹、缓存和反向传播设置下也一定单卡可跑。

这里仅需做一次有代表性的实际生成—更新检查和显存测量，不要再次扩成几十项新验收。

六、现在应该怎样安排，不要等 4B 全写完才想起 8B
我的统筹决定是：

**当前四卡继续优先完成 4B 已冻结的主链。**与此同时，可以准备 Qwen3-8B 的精确版本、权重获取、配置差异和后续协议草案；非 Qwen 的选型也可以同步明确。这些准备不应修改当前环境依赖或挤占正在运行的主要作业。

**4B 完整结果出来后，冻结要在外部模型检验的命题。**不是必须等 4B 出正结果才允许扩模型，而是要清楚扩模型究竟区分什么：小模型特例、测量粒度问题、映射关系变化，还是某个配方的局限。

**8B 与非 Qwen 的验证都保留，但不默认各跑两个阶段。**4B 承担阶段主研究，8B 承担较完整的规模复验，另一家族承担更小的针对性确认。这就是“小模型做深，其他模型验证关键结论”，而不是“三个模型各做一遍全部研究”。

因此，我上条的时间判断也应按这个完整范围理解：拿到 4B 主表和能写初稿，不等于三模型实验全部结束。没有测过 8B／另一家族的真实运行成本，就不能把它们当成顺手补几行表的工作。

最终计划没有变成只做 4B：4B 主研究＋Qwen3-8B 规模验证＋一个非 Qwen 家族的真实 RL 复验。闭源和真正的跨架构比较后置。我们应该减少的是重复探索和不必要的全排列，不是悄悄删掉已经讨论过的关键验证。

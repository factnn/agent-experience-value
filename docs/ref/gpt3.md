看到了，这次 main 已经更新到 ba98054852dc…。我读了新增的 11、12，对照了训练记录、配对统计、格式归一化脚本，以及部分逐题原始输出。这次有了正式规模的训练后评测结果，不再只是之前的 16-step smoke test；但下面的审查不等于我独立重新训练复现了一遍。
我的结论是：这轮实验有实质价值，暴露了当前实验设计的一项重要风险；但 12 对结果的几处解释又走得比证据远了一点。既不能据此杀掉整个研究，也不能据此宣布“核心 pilot 已经通过”。
一、这次真正测到了什么？
这次实际训练了 1,499 条随机轨迹，总输入约 22.39M tokens，其中约 8.37M 是监督 tokens；LoRA rank 16、学习率 2e-4，训练 1,499 步，记录耗时约 2.49 小时。注意，这里目前只有一个随机训练集，严格说还不是“不同策略之间的 token-matched 对照实验”。
同题、同预算的 BFCL 比较是：
测试轴	题数	Base 官方准确率	SFT 后官方准确率	变化	SFT 后归一化诊断分数
Java	100	65.0%	22.0%	−43.0pp	54.0%
JavaScript	50	70.0%	26.0%	−44.0pp	52.0%
Python	400	93.25%	67.5%	−25.75pp	75.0%


官方分数及逐题翻转统计来自配对结果；最后一列是仓库的后处理诊断，不是官方 BFCL 成绩。
这里有两件可以认真说的事情。
**第一，这个检查点的 BFCL 退化是大幅度的，不是两三道题造成的轻微波动。**Java 上甚至是 43 道从对变错、没有一道从错变对。不过，当前置信区间是对这两个固定检查点的题目重采样，不是多个训练种子的区间，所以还不能推广成“这套训练配方每次都会下降这么多”。
**第二，输出格式确实承担了相当一部分失败。**我看了原始 Java 输出：有的把本应直接输出的函数调用包进 Markdown 围栏，有的输出 function_calls 信封，有的输出 func_name/params 字典，随后被当前官方解码路径拒绝。这不是凭 loss 曲线猜出来的，是输出里能直接看到的。
但最稳妥的表述是：
在这一次训练设置下，模型对目标接口的输出约定发生了明显变化，造成大量官方评测失败。

还不能直接升级为“终端 SFT 一定破坏工具能力”，也不能断定这些结构就是从训练集中的某个具体格式复制来的。
二、12 的 NO-GO，到底该怎么理解？
保留原判据、如实记录没有通过，是对的；但原判据并没有准确检验我们真正关心的问题。
11 把“至少一个 BFCL 轴正向提升”设成研究可行的条件。于是这次所有轴下降，按它的字面规则确实是 NO-GO。
可是我们的研究并没有假设：
随机抽一批终端轨迹做 SFT，必然提高跨接口的 BFCL 分数。

因此，这次失败不能直接否定“不同经验的训练价值是否不同”这个研究问题。
但 12 提出的反向解释也不成立。它说：
训练产生了可测变化，所以“不同 bin 的差异恒等于零”这个可能性被排除了。

实际上：
\[
M(\operatorname{Train}(\pi,S))-M(\pi)\ne 0
\]
并不推出
\[
M(\operatorname{Train}(\pi,S_A))
-
M(\operatorname{Train}(\pi,S_B))
\ne 0.
\]
比如所有经验组都把模型拉低 30pp，那么“训练效应”很大，“选择哪种经验的效应”仍然可能接近零。反过来，Random 没有净提升，也不意味着某个选择策略不能改善结果。12 目前只有 Random 的结果，还没有测这个组间问题。
所以我不建议简单把门槛从 Δ > 0 改成 |Δ| > MDE。这只是从“要求正向变化”变成“要求任意变化”，仍然没有检验经验选择的价值。
这轮应当记录为：
Random-SFT 对 BFCL 的跨接口影响：观察到大幅负向变化。经验选择效应：尚未测量。

这比笼统的 GO／NO-GO 更准确。
三、我抓到了一个新的实质问题：多轮解析统计还没有测对
上次那个“decodable=True 写死”的问题，代码确实改了。但新的统计仍然有一个概念错误：
“能不能被函数调用解析器解析”，不等于“这次响应是否合法”。

具体证据就在：
smoke/eval_bfcl/mt16_parsestats_full/multi_turn_base_1.json
这道题最终 valid=true。它有 8 次模型响应，其中 4 次是工具调用，另外 4 次是正常完成说明，例如：
“The 'log.txt' file has been successfully moved into the 'archive' directory.”

然而这四段正常回答全部被计成了 parse_failed，所以这道成功任务的 decodable 被算成 0.5。
因此，09 新写的：
“真实格式失败率为 17.2%。”

**目前仍然不能成立。**准确的说法只能是“17.2% 的响应触发了解析器异常”，其中包含多少正常自然语言回答，还要重新分类。
同样，当前的：
\[
\frac{\text{executable calls}}{\text{all responses}}
\]
应该叫 工具调用响应占比，不能直接叫解析成功率。一个 agent 每次调用之后都正常总结，其占比可能只有 50%；另一个 agent 不断重复调用、不作总结，占比反而可能接近 100%。后者不因此更好。
**这里不需要重新跑模型。**先利用已经保存的响应，区分正常最终回答、明确的调用尝试、格式错误、未完成输出；不确定的另列，不要强行塞进错误类。
另外，新代码虽然保存了完整 raw，但 handler.inference() 仍然设置 exclude_state_log=True，返回的 metadata 也没有被保存。现在的完整文件主要是模型响应记录，还不是文档所说的“包含完整执行反馈、状态和停止原因的轨迹”。这会限制后续根因判断。
四、归一化诊断有价值，但“74.4% 是纯格式原因”要降一下表述强度
我同意保留这组诊断。Java 上从 22 道正确恢复到 54 道，很有信息量。
但脚本实际上使用的是：
r['valid'] or correct(..., normalize(r['output']))


即：**原来判对的保留；原来判错的，再尝试归一化救回来。**所以这是一个“官方判定或归一化判定任一通过即可”的诊断，不是所有输出经过一个固定转换器后重新评分。
它支持的结论是：
当前这套后处理规则能挽回 Java 上 32 道失败，缩小 74.4% 的官方分数差距。

但还不充分支持：
“我们已经确定 74.4% 的退化由纯序列化造成，而且这是严格下界。”

因为还需要审计转换是否始终保持函数名、参数名、参数值、类型、调用顺序和调用数量不变；尤其需要避免模糊输出在修复时被重新解释。此外，规则继续扩展时，也可能救回 Base 的额外错误，净差距未必只朝一个方向变化。
**下一版建议保留官方分数作为正式结果，把归一化明确叫“后处理可恢复性诊断”。**固定规则，对 Base 和所有训练组一致应用，保存每道题的转换前后文本以及新救回／新破坏的数量。这不需要新的模型实验。
条件正确率也不能独自代表“真实能力”
我前面建议报告 \(P(\mathrm{Correct}\mid\mathrm{Decodable})\)，作为辅助诊断是有用的，但不能把它当成完整的语义能力指标。
比如 Java：
- Base：65/93；
- Trained：22/27。
两边分母对应的不是同一批题。Trained 可能只是把较难的题都变成了解析失败，剩下的 27 道比较容易，因此条件正确率上升也不代表语义能力提高。同理，Python 条件正确率下降，不能仅凭两组区间是否重叠就完成“真实能力退化”的归因。当前脚本确实是在各自可解析的题目集合上分别计算。
可以额外比较“两边都可解析”的共同题目集合，但它仍然只是局部诊断，不能替代完整任务集的准确率。
五、这轮结果对我们的研究意味着什么？
它没有让我们必须缩 scope，也没有要求我们转去做一篇“BFCL parser 修复论文”。
它告诉我们的，是这条实验路线存在一个必须控制的因素：
\[
\text{经验训练}
\longrightarrow
\begin{cases}
\text{任务解决行为变化}\\
\text{输出接口约定变化}\\
\text{长度、停止与重试行为变化}
\end{cases}
\]
而官方任务分数测量的是这些因素共同作用后的结果。
这并不意味着官方分数“没意义”。**真实 agent 不遵守工具接口，本身就是实际失败，不能随意把这部分损失扣掉。**但如果论文进一步讨论“什么经验教会了可迁移的解决问题能力”，就不能只拿这个总分直接归因。
因此，12 里下面两句话目前都应该收回：
“所有 bin 训练后在 BFCL 上都会更差。”

只测了 Random，其他 bin 还不知道。
“叙事必须改成哪种经验破坏更小。”

现在也没有必要改。我们的原问题本来就允许经验价值为正、为零或为负。如果某类经验确实在近迁移上有收益、远迁移上有损失，这也是经验价值的一部分，而不是必须回避的结果。
六、接下来我建议做的，不是继续扩大检查清单
这次不再加一堆“正式实验之前还必须完成”的关卡。把已有证据用起来，下一轮集中做一个最小闭环。
先评现有检查点的近迁移，不急着再训练
Base 和已经训练好的 random1500，先在一组现有、可执行、未用于训练的终端任务上做同题比较。
这一步要回答：
这个模型是学到了终端任务行为，同时损害了 BFCL 接口兼容性，还是这套 SFT 配方整体就没有产生有用学习？

前者支持“收益与副作用并存”；后者说明应先修训练配方或数据处理，暂时不适合扩大到很多经验组。
当前仓库仍把训练任务 verifier／关联问题列为未解决，因此这条近迁移测量还需要落地。**不过，训练池缺少旧轨迹的成功标签，并不等于所有经验价值都不可测：它直接阻塞 Success 筛选等特定对照；只要有可靠的独立评测任务，Random、兼容性或多样性等策略的训练后效果仍可测。**我们不能把一种标签缺失无限扩大成整个研究无法开展。
配方校准只改一个因素
12 建议低学习率对照，这个可以做，但应保持同一数据、同一 rank、同一训练 token 暴露量，只改变学习率。不要同时降学习率、降 rank、改输出格式，否则即便恢复了也说不清为什么。当前 2e-4 只是一套已经测过的设置，不能凭分数下降直接认定它一定过高。
而且选配方不能只看“BFCL 掉得少”：学习率无限趋近于零，自然最接近 Base，但也可能几乎没学东西。要同时看来源相近任务是否产生学习收益，以及跨接口性能损失。
然后直接做第一组经验选择对照
在可用配方下，先比较 Random 与一个能可靠实现的选择策略。同池、同来源配额、可比长度与训练预算，保留独立重复；暂时不要一次铺开全部 proxy。
这一轮才真正测：
\[
\boxed{
M(\operatorname{Train}(\pi,S_{\text{selected}}))
-
M(\operatorname{Train}(\pi,S_{\text{random}}))
}
\]
而不是继续只测 Base 对一个 SFT 检查点。
最后给你一个不反复摇摆的判断
大 scope 不变，当前结果也不构成杀题依据。
这次新增实验已经给出了一个可信的、但条件有限的发现：
这套 Random-SFT 设置明显损害了 BFCL 表现；其中不少失败可以通过输出格式后处理挽回。

还没有得到的是：
哪一种经验比另一种经验更有训练价值。

所以，**继续做，但不要把“模型被训练改变了”当作“经验选择研究已经有信号”。**先修正现有统计解释，用现有检查点评一次近迁移，然后尽快拿到第一张真正的 Random vs. Selected 对照表。
这才是在我们冻结的大问题上往前走，而不是继续围着“这个项目到底 GO 不 GO”写文档。

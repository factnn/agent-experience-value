1. 为什么会走到 SFT？
当时我的思路是：你一个人、资源有限，公开的 teacher trajectories 又现成可用，于是先用较容易控制的 SFT，测“不同经验训练进去之后，迁移效果有什么不同”。

这个安排可以成为一个独立的 SFT 数据研究，但不能自动成为 RL 研究的代理实验。

问题就在这里：我们原本关心的是——

Agent 通过什么样的交互，能在 RL 中学到更多可迁移能力？有限交互预算应该花在哪里？

后来实施的却变成——

从别人生成好的轨迹里挑哪些，让学生模型模仿，效果更好？

这两个问题有关联，但不是同一个问题。我把“更容易开始做的实验”，不知不觉当成了“足以回答原问题的实验”。这是需要纠正的地方。

3. 因此，刚跑出来的实验应该怎样定位？
它是当前终端轨迹 SFT 的跨接口迁移实验，不是 RL 可行性实验。

它可以告诉我们：这批示范在这套 SFT 配方下，会怎样改变 BFCL 输出和成绩。它不能告诉我们：

RL 在这些环境里能不能学到东西；
哪种交互经验对 RL 更有价值；
不同 RL 经验分配策略是否有迁移收益差异。
所以，**不能用这次 SFT 在 BFCL 上下降，来给 RL 研究判 NO-GO；也不能因为下降幅度大，就说 RL 研究已经有可测信号。**当前训练记录确实只有这套 SFT 干预，没有对应的 RL 对照。

前面的数据审计、评测接口、日志和格式诊断可以保留；但继续优化 SFT 学习率，不应该再成为进入 RL 主实验的前置关卡。

5. 下一步该看什么？
不是继续问：

“Random SFT 能不能把 BFCL 训好？”

而是先完成一个真正的 RL 基线闭环：

同一初始 agent，在已有、可重置且有可信奖励的环境中，能够持续生成 rollout、计算奖励、更新策略，并在独立任务上被评测。

这之后再比较 均匀采样 RL vs. 某个经验分配规则的 RL，才第一次碰到我们的核心问题。

SFT 可以保留为共同的冷启动，或者之后的对照，但它不是必需的主研究对象；若使用冷启动，各 RL 组必须从同一个检查点开始。具体是否需要它，应由基础 agent 能否正常交互决定，而不是因为我们已经写好了 SFT 管线。

所以这次要纠正的不是“把 SFT 换成一个更时髦的算法”，而是把主实验重新对齐到你原本要问的学习问题：RL 中，什么经验真正产生可迁移能力。之前 SFT 那条路可以留下，但不能再替主线作决定。

**对，你抓到了在线 RL 的一个主要成本来源：它不仅要“学”，还要不断“自己做题／执行任务”，把新的交互经验生成出来。**在 LLM 的在线训练中，生成本身经常就是主要瓶颈，TRL 的官方文档也明确指出这一点。

这只是成本分账，不代表墙钟时间简单相加——有些环节能够并行。

**生成这笔账。**模型要自回归地生成下一步内容；一条轨迹内部有顺序依赖，不是把已经写好的文本读进去就行。多条轨迹可以批量并行，但不能消除单条轨迹的依赖。

**多次尝试这笔账。**例如 GRPO 通常对同一个问题采一组回答，利用组内奖励构造优势。因此训练单位不是简单的“一道题、一份现成答案”。当然，GRPO 省去了 PPO 中单独的价值模型，也是在减少另一部分成本。

**环境这笔账。**对于 agent，还要实际调用工具、维护状态、重置环境、获得奖励。一个本地计算器和一个需要安装依赖、运行测试的代码仓库，即便最后都产生一条 trajectory，执行成本也可能差很多。现有工具型 GRPO 实现也专门区分无状态工具和带 reset、状态与奖励的环境。

所以，贵的不只是“再生成一些 token”，而是持续运行完整的交互闭环。

不过公平地说，SFT 的示范数据也不是凭空来的。我们用别人已经发布的轨迹时，是省掉了自己采集它们的成本，不是这笔成本从来不存在。

3. 那 RL 的旧数据不能重复用吗？
能，但要看算法。

即使是 GRPO，也不是每做一次梯度更新就必须把整批轨迹扔掉：一批生成结果可以支持多次更新，原算法和现有实现都有相应设计。但这不等于可以无视策略变化，永久把旧轨迹当成当前策略采出来的。

另外，离策略 RL、离线 RL 本来就在研究怎样利用已有经验。离线 RL 甚至可以完全不追加在线采样，只用之前收集的数据；代价是要处理数据覆盖不足、学出的策略偏离数据分布等问题。它不是“把旧轨迹加个 reward，然后随便套在线算法”那么简单。

因此，准确的说法是：

我们现在想研究的在线 agent RL，通常需要持续补充新经验；不是 RL 这个领域的所有方法都必须这样。

4. 所以，当时转成 SFT，是因为成本吗？
**是，减少采样成本和工程复杂度，确实是我当时建议从 SFT 开始的理由。**但我们并没有先测量 RL 的实际开销，再得出“预算承担不起”的结论。

这两件事必须分开：

“SFT 更方便开始做。”

不等于：

“SFT 可以替我们回答 RL 的问题。”

所以正确的取舍应该是：保留 RL 这个研究对象，缩小模型、环境范围和对照数量，而不是把学习机制换掉。

我的建议是先用一个已有的、可重置且奖励可信的环境，固定一种 RL 算法和一个模型，先做均匀分配与一种经验分配规则的对照。先实测采样、环境执行、更新各占多少成本，再决定能承受多少条件和重复次数。现在还不该凭 SFT 的训练耗时，推算整个 RL 项目一定便宜或一定昂贵。

5. 而“现场生成很贵”，恰好强化了我们原来的研究动机
你最初问的其实就是：

我有有限的交互预算，让 agent 去经历什么，最值得？

在线 RL 下，这个问题包含两个不同环节：

环节	要决定什么	主要可能节省什么
采样之前	下一批去哪些任务、环境交互？每个分配多少尝试？	生成和环境执行成本
采样之后	已经获得的轨迹怎么利用、重放或加权？	更新成本，或提高已有经验的利用率
**如果我们关心的是“RL 现场生成太贵，怎样把预算花得更有效”，第一层尤其直接。**轨迹已经生成完才筛选，不能把之前消耗的采样成本省回来；只报告“训练用了更少的轨迹”，也不等于整个流程更省钱。

所以我的判断是：在线 RL 通常更贵，但这不是绕开它的理由，而是我们研究经验分配为什么有实际价值的原因。应该缩实验规模，不应该换掉原本要研究的学习机制。

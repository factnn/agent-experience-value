这些数字在审计记录和训练组记录中一致。此前失败尝试另外生成了 1,016 token，所以 66.6 秒不能当作整个接入过程的总耗时。
这里要把“完整推进”说准确：不是八条轨迹都正确完成任务，而是控制器成功处理了所有用户轮次，没有中途因接口或长度停止。
这次真正解决的是：
后续用户消息按照真实轮次进入上下文；模型输出、工具反馈、用户消息分别记录；原始生成 token 没有被重新改写；外部消息被排除出策略损失；整段交互可以交给 GRPO 计算奖励和优势。

**它解决了一个必要的接口障碍，但“optimizer 执行了两步”不能写成“模型已经在这个 benchmark 上学起来”。**两组优势都是零，参数也没有变化，仓库现在没有混淆这一点。
二、零奖励的原因，不是再把长度加大就行
这次没有轨迹触顶。因此，不能继续沿用此前“主要是生成预算不够”的解释。
重放诊断把 18 个失败的用户轮次分为：
- 11 次状态不匹配；
- 7 次必要执行响应不匹配。
车辆任务中，模型在引擎启动等操作返回错误后结束请求；文件系统任务中也有目录处理错误后没有修复。这些记录支持“存在真实的执行和反馈利用失败”，不是单纯的日志或输出序列化故障。
但其中一条轨迹值得单独看：
文件系统任务的三个用户边界，模拟状态都与参考一致；其中一个读取步骤使用 tail，返回 last_lines，而官方必要响应检查要求包含 file_content，于是整条轨迹得零。

这里不能直接下两个极端结论：
不能说“状态一样，所以模型其实完全正确”。只读任务即使什么都不做，状态也可能一样，还要检查实际读到了什么、回答了什么。
也不能说“官方给零，所以模型完全没有完成用户目标的能力”。当前检查包含特定执行响应要求，它与更宽泛的任务语义是否完全等价，需要具体核对。
对我们原 scope 的意义是：
\[
\boxed{\text{训练奖励与最终评价究竟测什么，必须写清楚。}}
\]
否则，之后发现某类经验“价值更高”，可能部分是在更快学会满足这套检查要求，而不是更广泛的任务解决能力。
**这不是让你现在另开一篇 reward paper。**保持官方结果不变，对这些已出现的开发样例做小范围语义审查即可；不要为了制造非零梯度，临时把奖励换成“状态相同就给分”。
三、一个具体代码问题：同批轨迹会互相压缩长度预算
这个问题在新增的 accept_bfcl_grpo.py 与 TokenEpisode.accept() 的组合中。
生成时用了：
budget = min(    1024,    min(e.budget - len(e.completion_ids) for e in active))


也就是，整个 active batch 都使用剩余预算最少的那条轨迹所允许的长度。
接收输出时又规定：
if ids[-1] != self.tokenizer.eos_token_id:    self.stop_reason = "generation_cap"    return


只要本段生成没有遇到 EOS，就直接终止这条轨迹。
考虑这个例子：
A 还剩 64 token；B 还剩 3,000 token。
两条一起生成，统一上限被设成 64。
B 在这 64 个 token 内没有结束，于是被判 generation_cap，直接终止。

B 明明还有充足的自身预算，却因为同批的 A 剩余预算少而提前停止。
这是代码逻辑能直接推出的边界问题。它没有解释本轮的失败——这轮八条都以 completed 结束；但后面打开较长推理、不同任务长度差异增大时，它可能产生偏差。
对我们尤其重要，因为它会让：
\[
\text{某条轨迹的结果}
\]
额外依赖：
\[
\text{同批其他轨迹已经消耗了多少 token}.
\]
最直接的修复是：按本次可生成额度分桶生成，例如按 min(1024, remaining_budget) 分组，而不是所有 active 样本取共同最小值。这样继续保留原先的单段上限和总预算，不需要改变实验目标。
加一个针对“A 剩 64、B 剩 3000”的回归测试就够了，不需要因此另造一套采样框架。
四、下一轮不能只把配置里的 thinking 改成 True
当前报告明确说：**关闭 thinking 是接口验收配置，不是选定的主研究配方。**这点需要保留，不能把这两道题的零奖励直接当作 Qwen3-4B 在 BFCL 上不可训练的证据。
我还注意到，enable_thinking=False 不只在 GRPO 配置里出现，也直接写在：
- TokenEpisode 初始 prompt 的模板调用；
- 后续外部消息桥接后，新增 generation header 的模板调用。
因此，**只修改 GRPOConfig.chat_template_kwargs，并不能让这条自定义生成路径完整切换模式。**需要把同一个显式配置传入初始化和后续桥接，同时核对实际生成前缀。
这不代表“打开 thinking 就一定能学”。它只是说明：下一次做模式比较时，要确保比较真的发生，而不是配置文件改了、实际输入没改。
五、从原 scope 看，现在应该继续什么，不应该继续什么？
**研究方向没有再次跑偏。**这次是在为已有 benchmark 的真实交互补必要接口，不是在重回 SFT，也不是为了省事把多轮任务替换成单轮任务。
但目前仍然停在：
\[

\]
距离我们需要的：
\[

\rightarrow
\text{受控 RL 干预}

\text{ID／迁移收益}

还缺实际学习信号和科学对照。
我建议下一步保持非常明确的边界：
先做一次有边界的开发校准，不在全零组上继续空更新
固定开发任务清单，覆盖不止两个单工具任务；预先确定少量配置，例如当前非推理配置与正确接入的推理配置。先只采样，记录完整任务成功率、逐轮表现、混合奖励组、错误类型和成本。
不要根据哪道题刚好成功，再把它选成研究任务；也不要把两个任务、八条轨迹的零奖励推广成整个任务池没有学习信号。
这次需要回答的是：
在正常、可说明的开发配置下，当前 learner 能否在多个任务上产生真实终局成功与失败，而不是只有接口通了？

一旦得到可用信号，就进入共同起点的短程分叉
不要再继续完善所有可能的工程角落。沿用已经建立的完整状态恢复，从共同起点比较不同分配条件，并同时测：
\[
G=\text{相对共同起点的收益},
\qquad
V=\text{相对 Uniform 的收益}.
\]
**Frontier、Coverage 都只是要检验的价值假说，不是必须证明更好的方法。**最终还要看这些信号能否预测未参与规则选择的干预收益，而不是只给出一个方法排名。
若开发校准仍大面积零奖励，就针对记录中的主要原因处理：接口误用、反馈利用、任务难度或奖励约束。可以调整实验承载环境或共同训练配方，但不能靠放松评测、偷偷加入答案，或者重新用 SFT 代替 RL，让结果“看起来能跑”。
最后，我对这版的判断
**这次完成的是“BFCL 多用户交互进入训练接口”，不是“BFCL 上已经有效学习”。**这个进展值得保留，零奖励也不构成杀掉原研究问题的依据。
当前最明确的执行顺序是：
修正批内长度耦合和模式配置传递 → 做一次限定范围的开发采样校准 → 有真实奖励差异后，直接进入共同起点的经验价值干预。

我不建议继续扩展通用框架，也不建议再写一轮宏观 GO／NO-GO 判断。我们现在需要保护的是：尽快获得第一批“采样前信号—RL 干预—迁移收益”的数据，而不是让工程验收本身变成项目主线。
